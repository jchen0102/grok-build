## 第 1 轮 — 为谁做、要不要登录

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 无登录 + 默认总览**（最合适） | 6–8h 全给导入和口径；空库仍像产品 | 提交物能被改数据；题面「权限」只能写进 README |
| B. 假登录 | README 能写一句鉴权 | 6–8h 浪费在题面没要的路上；和「不做登录」一致就不要做 |
| C. 默认进导入 | 空库不空 | 有数据时每次多点一次；不像日常看板 |

用户锁 A：平台 IC + lead；无登录；默认总览；空库停看板壳 + CTA。

---

## 第 2 轮 — 6–8h 完成标准

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 主路径竖切**（最合适） | 评分人 2 分钟能走通；和必做五项对齐 | 搜索/排序/导出等边角可能粗糙 |
| B. 四页都深 | README 每页都有故事 | 8h 内容易四页都半成品 |
| C. 先导入+总览，聚合/原始只 API | 口径先稳 | 前端缺两页，题面五项不完整 |

用户锁 A：导入 demo → 六指标+趋势 → 点异常数进聚合 → 原始记录可筛可翻页；同一时间窗。

---

## 第 3 轮 — 必做 / 选做 / 明确不做

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 必做做满，选做只留能加分的薄片**（最合适） | 必做五项不断层 | 要克制选做冲动 |
| B. 选做也做（异步导入、JSON、可配阈值、详情） | README 更长 | 必做五项变糙 |
| C. 必做也裁（趋势或原始只 API） | 8h 更松 | 题面五项不完整 |

用户锁：必做五项全做。选做全砍。趋势只按小时。一份静态 demo CSV。搜索 / 排序 / 分页仍做。明确不做登录、角色、审计、其它题、全部加分项。

---

## 第 4 轮 — 计算放哪

| 选项 | 利 | 弊 |
|---|---|---|
| A. 全在 SQL | ×1000 故事顺 | p95 / 双原因 / 测起来都别扭；6–8h 容易写错 |
| **B. PG 滤行，Go 算指标**（最合适） | 测试是纯函数；和网关习惯一致 | 1 万行闭区间要进内存 |
| C. 预聚合表 | 总览快 | 导入后还要滚表；空窗/重算；8h 超标 |

用户锁 B。可换实现的缝 = `internal/metrics`。×1000 只写 README。

---

## 第 5 轮 — 空态 / 错态 / 导航

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 一壳顶栏 + 廉价三态**（最合适） | 四页都像产品；时间窗能全局 | 导入页也在壳里，略重 |
| B. 总览单页，其余抽屉/弹层 | 少路由 | 聚合表和原始记录挤 |
| C. 无壳，各页自己管 | 实现短 | 时间窗和「异常数下钻」会裂 |

用户锁 A：廉价 loading/empty/error；顶栏四页；异常数 → 聚合 + 同窗 + `anomalous=1`；时间窗顶栏全局，导入页不读。

---

## 第 6 轮 — 导入语义

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 同步 + 分类明细 + 空 id 失败**（最合适） | 和题面「同步、有效行入库、失败行号原因」对齐；UNIQUE 允许多 NULL，空 id 必须当失败 | 大文件会卡住请求 |
| B. 异步 + job id | 像加分项 | 必做没要求；8h 超标 |
| C. 空 request_id 当 NULL 入库 | 少一个失败类 | Postgres UNIQUE 管不住，和「全局唯一」打架 |

用户锁 A：同步；流式+批量；成功/重复/失败；分类明细+样本封顶；空 request_id=失败；先到先得；只 trim；文件内先去重再插入。

---

## 第 7 轮 — 时间窗 / 时区 / p95

| 选项 | 利 | 弊 |
|---|---|---|
| **A. UTC + 闭区间 + nearest-rank ceil**（最合适） | 口径唯一；n=0/1 有定义；和「时区写清」对齐 | UI 不能用浏览器本地时区 |
| B. 浏览器本地时区 | 好看 | README 和测试都要解释偏移 |
| C. 开区间或未定义 p95 | 少写一句 | 评分人对着同一份 CSV 对不上数 |

用户锁 A：`timestamptz` UTC；默认窗=库内 min–max；`[start,end]`；小时桶 `[h,h+1)`；p95 = `ceil(0.95*n)` 1-based 夹到 n。

---

## 第 8 轮 — 异常 / 5xx / 样本

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 按题面：n≥20 且（5xx≥10% 或 p95≥1000）；4xx 不算错误率**（最合适） | 和题面一字对齐；双原因可测 | 没有「可配阈值」故事 |
| B. 4xx 也进错误率 | 像部分网关 | 和题面 5xx 字面冲突 |
| C. 样本只算 2xx | p95 更「干净」 | 题面没说；4xx/5xx 的延迟被丢掉 |

用户锁 A：规则按题面；两项都中则两个原因都展示；样本=全部入库状态码；总览异常数=时间窗内异常聚合行；n<20 列出不标异常。

---

## 第 9 轮 — 表结构

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 单表 + PK=request_id + 只要 ts 索引**（最合适） | 导入和去重是同一约束；6–8h 能讲清 | 没有批次追溯 |
| B. 另做批次表 | 导入可重放 | 8h 多一张表，题面没要 |
| C. 预聚合表 | 总览快 | 和第 4 轮 C 同一套成本 |

用户锁 A：`api_requests`；六列 NOT NULL；`latency_ms>=0`；不要 ingested_at / 批次 / 维度 / 预聚合。

---

## 第 10 轮 — HTTP API

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 四路由 + 部分成功 200 + page/per_page**（最合适） | 和四页一一对应；前端好接 | 没有 job 资源 |
| B. REST 资源更多（jobs、batches） | 看起来完整 | 题面没有这些页 |
| C. 部分成功当 207/422 | 语义更「准」 | 前端和评分人都要多解释 |

用户锁 A：overview / imports / endpoints / requests；`from`/`to` UTC 闭区间；`{error:{code,message}}`；部分成功=200；缺文件/缺表头=400；默认 20，上限 100。

---

## 第 11 轮 — 测什么

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 只测 p95 + 异常，表驱动密边界**（最合适） | 题面点名的口径；8h 测得完 | 导入/HTTP 无自动化 |
| B. 再加导入 + httptest | 回归更稳 | 挤掉 UI 时间 |
| C. 再加前端 E2E | 主路径可录 | 6–8h 必超 |

用户锁 A：n=0/1/20、乱序、19 vs 20、单/双原因、计数=行数。不测导入、不写 httptest、不做 E2E。

---

## 第 12 轮 — 提交形态

| 选项 | 利 | 弊 |
|---|---|---|
| **A. compose 一键 + demo.csv + ai-log/ 指针**（最合适） | 评分人能起来；对话不污染 README | 要维护 ai-log 目录 |
| B. 对话贴进 README | 少一个目录 | 考试把「README 必写项」和「AI 记录格式自定」分开了 |
| C. 只给二进制 / 不给 compose | 省事 | 和「docker compose up --build」字面冲突 |

用户锁 A。README 必写：导入策略、去重、p95、时区、性能、×1000。

---

## 第 13 轮 — 先竖切还是先铺底层

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 竖切**（最合适） | 任何时候停都有一条能演示的路径 | 前期 UI 会临时 |
| B. 先铺满 schema/API 再 UI | 接口一次定完 | 前 4h 没有画面 |
| C. 先 UI mock 再接 API | 看起来快 | 口径测试滞后 |

用户锁 A：表 → 导入 → 指标+测 → 总览 → 聚合 → 原始 → compose/README/ai-log。

---

## 第 14 轮 — 趋势 / 排序 / 搜索

| 选项 | 利 | 弊 |
|---|---|---|
| **A. 默认量+5xx 次数；异常优先；子串搜索**（最合适） | 空桶好解释；和「异常接口」叙事一致 | 默认看不到比率 |
| B. 默认就展示 5xx 率 | 质量感更强 | 空桶比率要定义 0 还是空 |
| C. 不做排序/搜索 | 省时间 | 题面原始记录要筛选；聚合表难扫 |

用户锁 A：可切 5xx 率；空桶次数 0、比率空；列可点排序；每页 20。

---

## 第 15 轮 — 主键 / 列表序 / 状态码

| 选项 | 利 | 弊 |
|---|---|---|
| **A. PK=request_id；ts DESC, request_id DESC + OFFSET；状态码 100–599**（最合适） | 去重=主键；排序稳定；和 HTTP 状态码常识对齐 | OFFSET 深翻页弱 |
| B. 另做代理主键，request_id 只 UNIQUE | 以后更好改 | 6–8h 多一列，无收益 |
| C. 状态码只允 2xx/4xx/5xx | 更「API」 | 3xx 被拒，和「全部入库状态码」样本定义打架 |

用户锁 A。
