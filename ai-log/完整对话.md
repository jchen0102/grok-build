## 题目 C：API 调用质量监控台

分类：数据／运营。输入是 CSV 调用日志，产出是导入、总览、趋势、接口聚合、原始记录。

### 必做硬核（丢了就明显扣分）

1. **导入**：校验列与格式；有效行入库；`request_id` 重复跳过（含文件内重复）；非法行不拖垮整批；返回成功/重复/失败数和失败行号原因；约 1 万行不能靠逐行 HTTP。
2. **总览**：时间范围内的请求数、5xx 率、平均延迟、p95、服务数、异常接口数。
3. **趋势**：按时间桶的请求量和 5xx（数量或错误率），桶策略要说清。
4. **聚合**：`service + endpoint + method`；异常规则写死：样本 ≥ 20，且 5xx 率 ≥ 10% 或 p95 ≥ 1000ms；两项同时满足要展示两个原因。
5. **原始记录**：时间/服务/接口/方法/状态码筛选 + 分页。
6. **工程**：迁移、演示 CSV 或生成方式、指标与异常的自动化测试、按查询设计索引。README 必须写：导入策略、去重、p95 算法、时区、性能、数据量 ×1000 的演进。

### 对你的利

- 和 MaaS 网关同构：service / endpoint / method / status / latency，名词不用临场发明。
- 没有角色矩阵，没有预约互斥，后端状态空间小，心智负担集中在「口径 + 导入」。
- README 里「×1000 演进」正好用网关/可观测经验（先索引和预聚合，再物化视图/rollup，再按天分区），这是 C 多出来的展示面，D 没有等价项。
- 正确性测试边界清晰：同一份夹具数据，总览数字、异常布尔、双原因展示可以对着算。
- 并发写冲突几乎不存在（最多两次同时导入），不容易在「409/原子性」上翻车。

### 对你的弊

- **口径陷阱比业务陷阱更阴**：p95 用 `percentile_cont` 还是 `percentile_disc`、空窗口、时区（CSV 是 `Z`、查询按本地日还是 UTC 日）、时间桶边界，都可能「页面有数但和测试不一致」。
- **前端更重**：上传结果摘要、趋势图、聚合表排序分页、原始日志。图和日期范围最吃时间，6～8 小时里这是 C 的主要超时点。
- **1 万行是硬约束**：Go 里逐行 `INSERT` 或前端逐行 POST 都不合格。必须流式解析 + `COPY`/批量插入 + 库内 `request_id` 唯一。AI 默认会生成逐行插入。
- **容易按生产网关过度设计**：异步队列、可配置阈值、JSON 接入全是可选项，做了不加分，挤掉必做。
- **完成感差**：看板永远能再美一点；评分不看美，但你会想继续做。
- 若岗位更偏「资源调度/控制面」，C 的互斥/状态机信号偏弱。

### 6～8 小时最可能没做完的

导入失败明细、p95 与异常测试、索引、趋势桶说明。页面四个都能点，但口径互相打架。

## 题目 D：公司设备预约与借用

分类：交易／资源调度。设备台账 + 半开区间预约 + 领用归还 + 员工/管理员。

### 必做硬核（丢了就明显扣分）

1. **角色**：前端只切换用户 ID；后端从库读角色，忽略客户端自称的角色；每项操作都校验。
2. **设备**：资产编号库层唯一；`maintenance`/`retired` 不能新建预约，也不出现在可用查询；**已有预约不因状态变化自动取消**。
3. **区间**：统一 `[start_at, end_at)`；点对点相接合法。
4. **创建预约**：`start < end`；员工只能给自己约；成功即 `confirmed`；`confirmed`/`checked_out` 占用时间；`cancelled`/`returned` 不占用；**并发两个冲突预约只能成功一个**。
5. **状态机**：`confirmed → checked_out | cancelled`；`checked_out → returned`；后两者终态。员工只能取消自己的 `confirmed`；管理员做领用/归还。超时仍 `checked_out` 则显示逾期。
6. **列表与历史**：员工看自己的；管理员看全部并可筛选操作；创建/取消/领用/归还与历史同请求原子写入。
7. **工程**：迁移与演示数据；区间重叠和状态流转测试；README 写区间语义、时区、并发策略、角色规则。

### 对你的利

- 和 GPU 借用同构：资源、占用窗口、领用/归还、管理员覆盖操作。并发占用是你熟悉的故事，README 能写清楚。
- **评分友好**：规则是对/错，评审可以按清单打：半开、相接、冲突 409、closed 类终态、角色。
- **前端更「表单+列表」**，没有图表和 CSV 大文件，页面工作量更可预测。
- 自动化测试好写：给定两条预约，断言重叠失败、相接成功、并发只一条。这比 C 的统计口径更容易写到「像那么回事」。
- 数据库有现成做法：`tstzrange` + GiST 排他约束（并排除非占用状态），比应用层 `SELECT` 再 `INSERT` 更贴题面「并发只能一个成功」。

### 对你的弊

- **规则密度高**：角色 × 状态 × 设备状态 × 区间，漏一条就是明显错。比 C 更容易「功能都有但规则没守住」。
- **GPU 经验是双刃剑**：审批、候补队列、抢占、超分、重复预约都是可选项或题外；写进去会显得没读题。可用性查询必须排除 maintenance/retired，但**不能**把已存在的 confirmed 预约藏掉。
- **时区 + 半开区间**和 C 的 p95 一样阴。存 `timestamptz` 还是 naive local，界面选「当天」时差一天，重叠判断会全错。
- **最低五块页面**（设备/可用性、创建预约、我的预约、管理员、详情历史），加上用户切换。范围比 C 多一块。
- **并发测试要动真格**：排他约束或事务冲突；AI 常写成 check-then-insert，单测过、并发挂。
- 若岗位明确是 API 网关/可观测/MaaS，D 的业务像「内部行政系统」，迁移叙事要自己补。

### 6～8 小时最可能没做完的

管理员筛选、逾期展示、历史原子性、并发测试。主路径能约能还，边角 409/403 不齐。
